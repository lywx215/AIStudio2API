# R3 主线保护、回退与上游更新

本手册描述将来的操作，不执行合并、提交、推送、部署或数据迁移。固定基线及用户既有改动见 [baseline.json](baseline.json)。保护范围和四接点见 [README.md](README.md)。

## 开关与版本回退

1. 在同一控制台读取 Business 配置及 revision，保存 `enabled=false`。配置写入仍需原控制台权限和版本检查；冲突时刷新后重试，不覆盖别人的新 revision。
2. 关闭只更换/停止 Business runtime，取消其在途请求。旧 AI Studio 的启停、WAA、账号库、配置和原 `/health` 含义不变。Business 请求仍明确报错，不落旧账号池。最终集成要验证采集任务和上传在关闭时的取消行为。
3. 保留 `runtime/business` 数据和原文件权限；关闭不等于删除，不自动删除上游会话。不要把本地文件删除报告成 Google 上游文件已删除。
4. 需要回到原发行版本时，先备份当前构建、配置和 Business Vault，再选择明确已知版本。Windows DPAPI 数据与当前 Windows 用户绑定；Unix 的目录/根密钥文件也属于秘密。不得把这些文件加入 Git 或输出到日志。
5. 源码撤销应只去掉四接点的附加语句、两个新增桥和附加实现，核对原 handler 的最终返回与管理分发。不用 `git reset --hard`、`git clean` 或恢复整个旧文件覆盖用户既有修改。数据迁移/删除需独立任务授权。
6. 回退后运行原功能与受管更新回归。二进制发布和部署需要届时明确任务；本手册不构成发布授权。

- 保存 fork 原有自定义补丁、四个挂接改动和新增模块的分别清单。用户已有 README/VPS 部署改动不并入 Business 功能。

- 确认固定参考包来源 SHA/摘要；第三方客户端或其 live 报告仅作协议研究材料，不能替代本分支验收。

## 在临时副本验证候选

1. 在授权的独立工作树或临时副本建立候选，先记录候选原本的测试结果，再应用 fork 与 Business 附加补丁。不要在当前并行开发目录做试合并。
2. 先检查四个接点语义：`runServer` 生命周期；API 完整原 handler 包装、管理优先级、原鉴权顺序和上传拦截器之前的 Business 续传分流；App 懒加载和 `TabID`。
3. 当前门禁固定基线及精确接点恢复规则。候选改动会使它失败，这是要求人工重评的信号。不能直接扩大 allowlist 或替换摘要消除失败；先审查候选原变化，再更新相应恢复规则与真实测试证据。
4. 在新增桥/附加模块适配候选变化，保护原 runtime/WAA/Gemini/files/auth/middleware/旧测试。若确实需要增加既有文件改动，先记录原因、范围和新的验收依据。
5. 运行边界/漂移门禁、完整 Go 与 Web 检查，并专门验证同对象一次委托、原管理路径、原别名优先、同 consoleAuth、模型 Key/管理权限、默认关闭无副作用、Business 文件与上传能力归属。双 WAA 的离线合同不能替代需另授权的 live 测试。
6. `git rerere` 只能辅助解决冲突；无冲突、构建成功或合成漂移通过均不能单独宣称兼容。不得自动修改 Git 配置。
7. 记录候选 SHA、冲突/解决办法、实际执行命令与退出码、环境阻断和未测项，再由主窗口判断是否满足离线里程碑。发布和部署独立授权。
